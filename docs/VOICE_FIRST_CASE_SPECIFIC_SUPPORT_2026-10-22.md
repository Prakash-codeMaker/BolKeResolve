# Voice-First Guided Chat + Case-Specific Support — 22 October 2026

## Product intent

Make the first useful action simple and specific. The user should be able to tell the story in their own language, inspect a concise next move, open the relevant official support destination, and prepare a message without needing a separate WhatsApp integration. The same case information should persist in the existing shared case engine after the user chooses to save it.

## What changed in this increment

- Added multilingual voice input to the in-site Guided chat. Ten Indian speech-language codes are selectable: Hindi/Hinglish, English (India), Marathi, Bengali, Gujarati, Kannada, Malayalam, Punjabi, Tamil and Telugu. The current path records on the device, sends audio to `/api/voice/transcribe` only after stop, and places the returned transcript in the composer for review. It does not auto-send or auto-save the transcript.
- Read-aloud controls use the browser Web Speech API in Guided chat. Available voices and pronunciation depend on the browser/operating system; if no usable voice is installed, typing and reading the text remain available. The existing case-draft read-aloud endpoint remains separate and uses configured server-side TTS.
- Voice input requires `GNANI_API_KEY`. Anonymous voice is gated in production-auth mode by `BOLKE_PUBLIC_VOICE_ENABLED` and a tighter rate-limit. This is an explicit paid-usage/privacy control, not an arbitrary UI limitation. Keep it disabled on public production until the privacy notice, cost limits, monitoring and retention behavior have been reviewed.
- Added `backend/support_directory.py`, a curated list of first-party platform or government routes for Google Pay, Paytm, PhonePe, Flipkart, Amazon India, Zomato, Swiggy, Uber, MakeMyTrip and IRCTC, plus relevant general official routes for National Consumer Helpline, NPCI UPI and cybercrime reporting. RBI CMS is a later, eligibility-dependent option and is not automatically added as a default escalation.
- Support routes are matched from the user's reported merchant/description/issue. The resolver returns no more than two destinations. Unknown merchant names do not create invented phone numbers or addresses. Suspected unauthorised/fraud cases put the cyber-safety route first.
- The recommendation contains an editable, unsent support draft. The saved-case overview now presents the relevant support route cards beside the primary next action. A button routes the user directly to the saved draft tab.
- External support links are rendered as HTTPS-only links; no links to unauthenticated third-party contact aggregators are generated by the directory. Links and guidance must be periodically reviewed because organisations change their help flows.

## Architecture / code map

- `frontend/index.html`: Guided chat shell, language selection, voice controls and live status.
- `frontend/app.js`: browser recorder, WAV encoding/resampling, transcription request, transcript review, resolution preview, official-link card renderer, message read-aloud, case save and in-case navigation.
- `frontend/design-v2.css`: responsive phone/chat shell and case-specific support card styles.
- `backend/main.py`: `/api/voice/transcribe`, `/api/extraction/preview`, `/api/resolution/preview`, case persistence and `add_support_context()`.
- `backend/support_directory.py`: curated support destinations, matching and preview draft helper.
- `backend/resolution.py`: deterministic issue routing and official source-backed playbooks.
- `tests/test_support_directory.py`, `tests/test_frontend_assets.py`, `tests/test_resolution.py`: support-directory precedence, route safety, draft boundary, UI affordance and API response regression tests.

## Expected user path

1. Select a common issue or tell the story in Guided chat.
2. If using voice, choose a language and record for up to 60 seconds; stop and review the transcript.
3. Send the text to the in-site chat. BolKeResolve prepares a source-backed recommendation without saving a case at this point.
4. Review one primary next action, matched support route(s), a draft to edit/copy, and the caveat that no organisation has been contacted.
5. Choose `Save case` only after review. The saved case overview then shows matching support links and direct actions for the draft, evidence and outcome.
6. The user opens the official channel and sends the reviewed message themselves; the user records any reply or outcome in the case timeline.

## Known limitations / do not overclaim

- The merchant directory offers official starting points and procedural guidance; it does not contact the organisation, verify merchant/payment records or submit complaints.
- Product support URLs can change. Run a periodic link review before public release and whenever users report a dead route.
- The matcher uses conservative rules and is not a merchant recognition model. It returns a small list; it should not be presented as a complete catalog.
- If the merchant is missing or mis-extracted, the user can correct case details and refresh the plan. Do not infer the merchant solely from a low-confidence extraction.
- Voice requires user gesture/microphone permission, localhost or HTTPS, configured Gnani credentials and any applicable usage quota. Device/browser speech synthesis may use a different voice than the selected STT locale.
- Keep browser STT text reviewable. A spoken word can be mistranscribed; users must confirm merchant, amount, date and transaction status before saving.
- The public preview rate limiter is in-process. A multi-worker deployment needs a shared limit at a trusted gateway/WAF or distributed store.
- This increment does not include automatic email sending, merchant APIs, complaint filing, a public accusation board, community case sharing, or push notifications.

## Responsive layout hardening added after screenshot review

- `.workspace-shell`, `.form-layout`, the form card, helper rail and case route grids now explicitly constrain width and permit grid children to shrink.
- At widths up to 900 px, the intake layout becomes one comfortable content column and moves the helper cards below the form; at narrow widths the helper and support-route cards stack into one column. This addresses clipping/overflow seen in the provided screenshots.
- Automated CSS guardrail tests verify these responsive rules are present. Actual mobile/desktop browser review remains a manual release gate because the build environment could not run local Chromium reliably.
